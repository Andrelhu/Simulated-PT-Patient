The six items

1
Landing page and pre-brief
Built

Standardized patient exams already have a convention for this: the door note, the information a candidate reads before entering the room. Borrowing it makes the pre-brief authentic rather than a help screen, and it sets up the assessment by naming the task.

The door note is case-specific and lives in character_meta.json, so faculty can edit it without touching code. The instructions below it are the same for every case: the patient will not volunteer information, the notes pad is saved with the session, the clock starts on Start and does not pause, and the encounter is recorded.

It is shown every time, with no dismiss option. In a timed assessment the pre-brief is part of the protocol, not onboarding a student has outgrown.

Added since the first draft

The student trial runs with no individual login. One shared class code gates the page, and a participant code is optional — entered, it links a student's sessions together; left blank, the session is stored under a random anonymous id. The public endpoint needed some gate regardless: without one, anyone finding the URL can consume model calls on the university's gateway.

2
Avatar photo
Route ready, image pending

The /avatar/<name> route serves a real image when one exists and otherwise generates a silhouette whose colour derives from the character's name, so characters stay visually distinct with no images present at all.

avatars/Ana.png        # .png .jpg .jpeg .webp all work

Square, at least 500×500, face centred. No restart needed; the file is read from disk per request.

Check before committing an image

If the photo is of a real identifiable person, it needs a signed likeness release covering educational use and redistribution — and if that person is a student or staff member, there are FERPA and HR questions on top. A generated or properly licensed portrait avoids all of it. Image files are deliberately gitignored: git history keeps a file even after it is deleted.

3
Ten-item assessment
Built

Keeping the feedback coarse was the right call, and worth saying why: it sidesteps the biggest weakness of automated grading. A three-bucket signal is far more robust to an inconsistent judge than itemized written critique, and it gives students nothing to reverse-engineer. The grader can be imperfect and the result still be fair.

Students see a single percentage of the topics expected in a subjective history for that case:

70% of expected topics Normalised over the items that actually applied. A student is never marked down for an item the encounter gave them no chance to meet.
The first draft guessed wrong here

This spec originally assumed the ten items would be case facts, different per character. Faculty delivered something better: one global list of process items — did the student introduce themselves, ask about mechanism, ask about function and goals. So there is one shared rubric.json, and the per-character ground truth comes from the character file the grader already reads.

Reading the actual items changed the design in two ways that matter:

Three items are conditional. Redirecting a patient back on topic can only be graded if the patient went off topic — and one character rambles while another does not. Marking a student red for failing to redirect a patient who never drifted would be scoring them on something that never happened. Those items return not_applicable and drop out of the denominator entirely.

Six items are compound — greet and introduce yourself, mechanism and prior episodes, pain quality and pain behaviour, function and goals. Each half is listed separately, so partial credit means one of two parts met rather than the grader's impression.

Each item is graded in its own model call returning strict JSON with an evidence quote. Students never see the quotes. Storing them is what lets faculty audit the grader, and it is the difference between a number that can be defended and one that cannot.

Still worth knowing

The model grading the encounter is the same model that played the patient. For the eight content items that is fact-checking against a transcript and holds up reasonably. For the two judgment items — empathy and redirection — it is weaker. Spot check a sample against a faculty rater before any of this carries a grade.

4
Exit survey
Deferred

Deferred deliberately. A survey object is reserved on the session record so encounters collected before the survey exists stay shape-compatible with ones collected after. Costs nothing now and avoids a migration later.

5
Emotional reaction, and whether it can be a metric
Logged, not graded

Two separate questions were tangled together here, and the order matters. Whether the model reacts emotionally appropriately is a question about the instrument, and needs human raters. How well the student communicated is a question you want to answer using the instrument. The second is not honest until the first checks out.

The character files already contain the measurement. One character rambles and loses focus when the student is unfocused; another opens up only when the student is warm and patient. The patient's behaviour over the encounter is therefore already a response to the student's communication — which means the metric can be an outcome rather than an opinion. Did the patient open up, or shut down?

What is recorded per patient message:

  • Valence (−1 to 1) and arousal (0 to 1) — Russell's circumplex, the standard dimensional model in affective computing. Continuous, so a trajectory and its slope can be computed.
  • A categorical label from Ekman's six basic emotions plus neutral — the standard categorical set, and the part faculty can actually read.

Scored in one batched call when the encounter closes, not inline, so it adds nothing to the latency a student experiences mid-conversation and can be re-run over sessions already collected.

Sequencing

The data is being logged now; the derived communication grade stays hidden until it is validated. Validation is a small study worth running anyway: around twenty sessions, faculty rate communication independently, then check whether the trajectory metric agrees. If it does, there is a defensible metric and the validity paragraph a paper needs. If it does not, the grade is dropped and the data is still there.

For publication in health communication, the discipline standard to align with is VR-CoDES (Verona Coding Definitions of Emotional Sequences), which codes patient emotional cues and concerns and whether the clinician's response gave or reduced space. It is what a reviewer in that field would expect.

6
Ten-minute timer that closes the session
Built

The one thing that could not be got wrong: the clock lives on the server. A countdown in JavaScript is edited away from devtools in ten seconds, and a page refresh resets it. For something carrying an assessment that is not good enough.

  • Start stamps started_at server-side.
  • Every message re-derives the remaining time from the stored session and is refused once the limit passes, so refreshing buys nothing.
  • The client countdown is display only, resynced against the server periodically, with a warning at two minutes left — the usual OSCE convention.
  • At zero the encounter closes with close_reason: "timeout" and grading runs. An encounter that times out with nothing said closes cleanly too, rather than stranding the student on a disabled screen.
  • No pause. An End button lets a student finish early, which matches how these exams run.

Tips for next time

Added after the first draft: one line of concrete advice under the results, composed from the items the student actually missed.

Built deterministically from the grader's own output rather than by asking the model for advice. It therefore costs no extra model call on an already slow close, and cannot invent guidance the grading did not support. Outright misses are named before partials, capped at three so it stays one line. The wording per item lives in rubric.json for faculty to edit, with the character's name substituted in.

Session record

One JSON file per encounter at sessions/<participant>/session_<id>.json, holding the transcript, the student's notes, the grading with its evidence quotes, the per-turn affect, and the tip shown. Writes are atomic and locked, because the service runs multiple workers and restarts automatically: a worker killed mid-write would otherwise leave a truncated file and lose the encounter.

{
  "session_id":       "…",
  "participant_code": "PT07",          // blank when anonymous
  "mode":             "trial",
  "character":        "Ana",
  "started_at":       "…",             // server-stamped; the timer reads this
  "duration_seconds": 600,
  "closed_at":        "…",
  "close_reason":     "timeout",       // or "ended_early"
  "exchange_count":   14,
  "notes":            "…",             // the student's scrap notes
  "exchanges":        [ { "question": "…", "response": "…" } ],
  "assessment": {
    "rubric_version": "pt-subjective-v1",
    "items":    [ { "n": 1, "result": "got", "evidence": "…" } ],
    "score":    { "fraction": 0.7, "counted": 8, "not_applicable": 2 },
    "tips":     "Next time, …",
    "affect":   { "overall": "amber", "trajectory": "became_guarded" },
    "sentiment":{ "turns": [ { "turn": 1, "valence": -0.4, "arousal": 0.6,
                               "label": "sadness" } ] }
  },
  "survey": null                       // reserved
}
